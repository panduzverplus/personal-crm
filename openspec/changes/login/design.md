# Design

## Context

Зачем — см. `proposal.md`, раздел Why. Требования — `specs/user-auth`, `specs/data-ownership`, `specs/contact-groups`.

Что есть сейчас:

- Входа нет. Все запросы к базе — в `src/lib/contacts.ts` и `src/lib/groups.ts`, их вызывают серверные компоненты страниц и действия в `src/app/actions.ts`. Ни один запрос не знает, кто пользователь.
- Таблицы `contacts`, `notes`, `groups`, `contact_groups`. Уникальность названия группы — глобальный индекс `groups_name_normalized_idx` по `replace(lower(name), 'ё', 'е')`. Миграция `0004_default_groups.sql` вставляет пять групп в любую новую базу, в том числе в тестовые.
- Миграции на сервере применяет `src/db/migrate.ts` в разовом контейнере `crm-migrate` (одно подключение, `max: 1`). Локально `pnpm db:migrate` вызывает `drizzle-kit migrate`. Тестовые базы создаёт `src/test/migrated-database.ts`.
- `src/db/seed.ts` заполняет базу, только если в ней нет ни одного контакта. На проде демо-данные уже залиты.
- e2e запускают собранное приложение на порту 3100 со своей базой `_e2e_test`; в CI база поднимается `pnpm db:up` из `compose.yaml`.
- Образ собирается один раз в CI. `next build` импортирует модуль базы, поэтому в `Dockerfile` для сборки заданы пустышки `POSTGRES_*`.
- На сервере nginx проксирует `app.chigabugadaga.ru` на `127.0.0.1:3000` и передаёт `X-Forwarded-For`.

Ограничения из спеки и `CLAUDE.md`: Better Auth с MagicLink, Nodemailer, Resend, Mailpit; права проверяются на сервере; миграции — отдельным шагом до старта образа; секреты только в `.env`.

## Goals / Non-Goals

**Goals:**

- Один путь к данным: каждая функция `src/lib/*` получает id пользователя и сама фильтрует по нему. Страница или действие не могут достать данные, не назвав пользователя.
- Одна миграция переводит существующую базу в схему с владельцами атомарно: либо всё, либо ничего.
- Лимит писем, отмена старых ссылок и проверка почты работают на сервере для любого запроса, не только из формы.
- Сценарии со временем (15 минут, 10 минут, 30 дней) проверяются автотестами без ожидания: время сдвигается в базе.

**Non-Goals:**

- Защита от массовой рассылки с разных почт, кроме встроенного лимита Better Auth по IP.
- Удаление пользователей и их данных: в приложении такого действия нет.
- Изоляция на уровне базы (Row Level Security): достаточно одного слоя запросов, покрытого тестами.

## Decisions

### 1. Better Auth: таблицы в схеме Drizzle, имена во множественном числе

Better Auth подключается через `drizzleAdapter` с `usePlural: true`: таблицы `users`, `sessions`, `accounts`, `verifications` — в одном стиле с `contacts` и `groups`. Описания таблиц генерирует `@better-auth/cli generate` (разово, через `pnpm dlx`, в зависимости не попадает) в `src/db/auth-schema.ts`, который реэкспортируется из `src/db/schema.ts`. Миграцию делает `drizzle-kit generate`, как для остальных таблиц. Id пользователя — текст, как по умолчанию в Better Auth.

Обработчик Better Auth — `src/app/api/auth/[...all]/route.ts`. Пароли не включаются (`emailAndPassword` выключен по умолчанию), подключён только плагин `magicLink`.

Альтернатива — свой вход на подписанных ссылках: меньше зависимостей, но спека требует Better Auth, а сессии, куки и одноразовые токены пришлось бы писать и проверять самим.

### 2. Ссылка: 15 минут, одна попытка, токен хранится хешем

`magicLink({ expiresIn: 15 * 60, allowedAttempts: 1, storeToken: "hashed" })`. Одноразовость и срок даёт Better Auth. Хеш в базе: утёкшая копия базы не даёт войти.

Ссылка ведёт на `/api/auth/magic-link/verify` с `callbackURL: "/"`, `newUserCallbackURL: "/"` и `errorCallbackURL: "/login/expired"`. Любая ошибка проверки (устарела, использована, отменена, испорчена) ведёт на одну страницу «Ссылка устарела»: человеку причина не нужна.

### 3. Отправка письма: лимит, отмена старых ссылок и письмо — в одной транзакции в `sendMagicLink`

`sendMagicLink` — единственное место, через которое уходит письмо, поэтому правила стоят там, а не в форме. Внутри одной транзакции:

1. `pg_advisory_xact_lock(hashtext(email))` — два одновременных запроса на одну почту идут по очереди, лимит не проскакивает.
2. Считаем строки новой таблицы `login_email_sends (id, email, link_identifier, sent_at)` за последние 10 минут. Три и больше — удаляем только что созданный токен и бросаем `APIError("TOO_MANY_REQUESTS")`. Прежние ссылки живут.
3. Удаляем из `verifications` ссылки прежних писем этой почты: их `identifier` лежит в `login_email_sends.link_identifier`.
4. Записываем строку в `login_email_sends` с `identifier` новой ссылки.
5. Отправляем письмо. Отправка упала — транзакция откатывается: письмо не засчитано, старые ссылки не отменены; новый токен удаляется.

Старые строки `login_email_sends` (старше суток) удаляются тем же запросом, чтобы таблица не росла.

Токен хранится хешем, который задаём сами (`custom-hasher`, SHA-256): так `identifier` новой ссылки (`magic-link:<хеш>`) известен коду, и его можно записать и удалить.

Отменять по порядку отправки, а не по порядку создания ссылок или по почте в JSON `value`, нужно из-за двух запросов одновременно: Better Auth создаёт токены до `sendMagicLink`, и письмо, ушедшее первым, не должно убить ссылку письма, которое уйдёт вторым. Так у письма, ушедшего последним, ссылка всегда жива. (Первая версия — «удалить все токены почты, кроме нового» — оставляла письмо с мёртвой ссылкой; поймано тестом на параллельные запросы. Время создания для порядка не годится: у одновременных запросов оно совпадает до миллисекунды.)

Альтернатива — встроенный лимит Better Auth: он считает запросы по IP и адресу, а не по почте, и не знает про «писем». Альтернатива — проверять в серверном действии формы: прямой запрос к `/api/auth/sign-in/magic-link` её обошёл бы.

От формата `value` в `verifications` (деталь Better Auth) код больше не зависит; остаётся зависимость от вида `identifier` — `magic-link:<сохранённый токен>`. Её закрывает тест «запрошена новая ссылка — старая устарела» на настоящей библиотеке: обновление, меняющее формат, уронит тест, а не тихо сломает отмену.

### 4. Проверка почты — одно правило, на сервере, для любого запроса

`src/lib/login-email.ts`: `parseLoginEmail(raw)` — обрезает пробелы, переводит в нижний регистр и проверяет тем же правилом, что поле «Почта» контакта (`z.email()` из `src/lib/contact-form.ts`, вынесенное в общую функцию). Вызывается:

- в серверном действии формы входа — чтобы показать «Проверь адрес почты» под полем;
- в `hooks.before` Better Auth для пути `/sign-in/magic-link` — запрос не из формы с неверной почтой отклоняется до создания токена, верная почта подменяется нормализованной.

Почта в `users` хранится в нижнем регистре, поэтому «Anna@Example.com» находит того же пользователя.

### 5. Форма входа — серверное действие поверх `auth.api.signInMagicLink`

Страница `/login` (клиентская форма + `useActionState`), действие `requestLoginLink` в `src/app/login/actions.ts` вызывает `auth.api.signInMagicLink` с заголовками запроса. Ответы: успех — «Ссылка для входа отправлена на <почта>»; `TOO_MANY_REQUESTS` — «Слишком часто, попробуй через несколько минут»; сбой отправки — «Не удалось отправить письмо. Попробуй ещё раз.». Для новой и известной почты путь один и тот же, разницы в ответе нет.

Страница `/login/expired` — статичный текст и кнопка «Получить новую ссылку» на `/login`.

### 6. Сессии: 30 дней, продление раз в сутки, без кеша в куке

`session: { expiresIn: 30 дней, updateAge: 1 день }`. Каждый заход, если с прошлого продления прошли сутки, сдвигает срок на 30 дней от сейчас. `cookieCache` не включаем: выход и истёкшая сессия видны сразу, лишний запрос к базе на страницу при таком числе пользователей не важен. Сессия — строка в `sessions` на устройство; выход удаляет только её.

### 7. Закрытость приложения: `proxy.ts` для перенаправления, проверка — на сервере

- `src/proxy.ts` (в Next.js 16 так называется бывший `middleware.ts`): нет куки сессии (`getSessionCookie`) — перенаправить на `/login`. Пропускает `/login`, `/login/expired`, `/api/auth/*`, `/health` и статику. Это только удобство: кука может быть поддельной или истёкшей.
- `src/proxy.ts` ещё и обновляет куку входа при каждом заходе на страницу (кроме серверных действий): Better Auth продлевает сессию в базе, но из серверного компонента не может поставить куку, и без этого кука в браузере истекала бы через 30 дней после входа, как бы часто человек ни заходил. Новая кука — те же атрибуты и значение, срок 30 дней.
- Настоящая проверка — `src/lib/session.ts`: `requireUser()` достаёт сессию через `auth.api.getSession({ headers })`; нет сессии — `redirect("/login")`. Её вызывает каждая страница с данными, `layout.tsx` (почта в шапке) и каждое серверное действие первой строкой.
- Функции `src/lib/contacts.ts` и `src/lib/groups.ts` получают `userId` первым параметром. Id никогда не приходит из браузера: только из `requireUser()`.

Альтернатива — проверка только в `proxy.ts`: документация Next.js прямо говорит, что это не защита, а серверные действия она не закрывает.

### 8. Владелец: `owner_id` у `contacts` и `groups`; заметки и связи — через контакт

- `contacts.owner_id` и `groups.owner_id` — `text not null references users(id)`, без каскадного удаления: удаления пользователей нет, а случайная потеря данных хуже ошибки. Индексы: `contacts (owner_id)`, уникальный `groups (owner_id, replace(lower(name), 'ё', 'е'))` вместо глобального.
- У `notes` и `contact_groups` своей колонки нет: принадлежность идёт через контакт. Каждый запрос к заметкам соединяется с `contacts` и проверяет `owner_id`.
- `replaceContactGroups` вставляет связи только с группами того же владельца — чужой id группы молча пропускается, так же как уже пропускается удалённая группа.
- Поиск, счётчики, «Пора связаться» и подзапрос названий групп в строке списка фильтруются по владельцу контакта; группы — по владельцу группы.

Альтернатива — `owner_id` и у заметок: проще запросы, но две правды о владельце, которые могут разойтись. Альтернатива — Row Level Security в Postgres: надёжнее, но требует роли и `set` на каждое подключение — сложнее, чем нужно приложению на нескольких друзей.

### 9. Миграция с владельцем: SQL читает почту из настройки сессии Postgres

Одна миграция (`drizzle-kit generate`, затем ручная правка SQL):

1. Создаёт таблицы Better Auth и `login_email_sends`.
2. Добавляет `owner_id` в `contacts` и `groups` пока без `not null`.
3. Блок `DO`: если в `contacts` или `groups` есть строки, берёт почту из `current_setting('app.owner_email', true)`. Пусто — `RAISE EXCEPTION 'OWNER_EMAIL is not set: ...'`. Иначе находит пользователя с этой почтой (в нижнем регистре, без пробелов) или создаёт его (`gen_random_uuid()::text`, имя пустое, почта подтверждена) и проставляет его id всем строкам.
4. Ставит `not null`, внешние ключи, меняет индекс уникальности названий групп.

Drizzle выполняет миграции в одной транзакции, поэтому ошибка на любом шаге откатывает всё: база остаётся как была, `deploy.sh` останавливается до старта нового образа, старый продолжает работать.

Почту передаёт `src/db/migrate.ts`: читает `OWNER_EMAIL` и до `migrate()` выполняет `select set_config('app.owner_email', $1, false)` на том же единственном подключении. Так же делают `src/test/migrated-database.ts` (тестовая почта владельца) и e2e. `pnpm db:migrate` переводится с `drizzle-kit migrate` на `tsx src/db/migrate.ts`, чтобы локально работал тот же путь.

Миграция только добавляет: ни одна строка `contacts`, `notes`, `groups`, `contact_groups` не удаляется и не меняется, кроме `owner_id`.

Альтернативы: почта в тексте миграции — владелец выбрал настройку в `.env`; отдельный скрипт после миграций — тогда `not null` пришлось бы ставить ещё одной миграцией, и между ними приложение жило бы с записями без владельца; «первый вошедший получает всё» — владелец отказался.

### 10. Письма: Nodemailer по `SMTP_URL`, Resend по SMTP

`src/lib/mail.ts`: `nodemailer.createTransport(process.env.SMTP_URL)`, транспорт создаётся при первой отправке.

- Компьютер и автотесты: `SMTP_URL=smtp://127.0.0.1:1025` — Mailpit.
- Сервер: `SMTP_URL=smtps://resend:<API-ключ>@smtp.resend.com:465` — SMTP-шлюз Resend.

Код один, разница только в строке настроек. Отправитель — константа `"Личная CRM" <noreply@mail.crm.chigabugadaga.ru>`. Письмо — HTML с кнопкой «Войти» и текстовая версия, собираются функцией `loginEmail(url)` в `src/lib/login-email.ts` (без шаблонизаторов).

Альтернатива — SDK Resend: спека требует одну библиотеку для заглушки и Resend, а SDK в Mailpit не отправит.

### 11. Mailpit в `compose.yaml`

Сервис `mailpit` (образ `axllent/mailpit`, тег — последняя стабильная версия на момент реализации), порты `127.0.0.1:1025` (SMTP) и `127.0.0.1:8025` (страница и API), проверка готовности `mailpit readyz`. `pnpm db:up` поднимает его вместе с базой и ждёт обоих — в CI ничего добавлять не нужно. На сервер Mailpit не попадает: `deploy/compose.yaml` не меняется.

### 12. Настройки и сборка

Новые переменные: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, `OWNER_EMAIL`. Все — в `.env.example` без значений и в таблице README. `next build` в `Dockerfile` получает пустышки для `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL`, как сейчас для `POSTGRES_*`: при сборке никто не входит и писем не шлёт.

Встроенный лимит Better Auth по IP оставляем, но для `/sign-in/magic-link` задаём своё правило — 10 запросов в минуту: стандартное (3 за 10 секунд) мешало бы проверке лимита писем и не нужно при лимите по почте. IP Better Auth берёт из `X-Forwarded-For`, который ставит nginx.

### 13. Тесты

- Vitest (настоящая тестовая база): изоляция в каждой функции `src/lib/contacts.ts` и `src/lib/groups.ts` — два пользователя, чужой id ничего не отдаёт и не меняет; `parseLoginEmail`; лимит, отмена старых токенов и откат при сбое отправки в `sendMagicLink` (почта — подменённый транспорт); миграция владельца — база доводится до `0004`, заполняется, затем применяется новая миграция: владелец создан, всё у него, число строк то же; без почты — ошибка и база прежняя. Для «довести до 0004» — помощник, который применяет миграции из временной папки с обрезанным журналом.
- Playwright: `e2e/mailpit.ts` (найти последнее письмо получателю через API Mailpit, достать ссылку) и `signIn(page, email)`. Перед каждым тестом письма в Mailpit удаляются. Новый `e2e/login.spec.ts` — главный сценарий входа, A и B, устаревшие ссылки, лимит, шапка и выход, срок сессии. Сроки сдвигаются в e2e-базе (`verifications.expires_at`, `sessions.expires_at`/`updated_at`, `login_email_sends.sent_at`), а не ожиданием.
- `e2e/main-scenario.spec.ts` и `e2e/keep-in-touch.spec.ts` сначала входят под пользователем; `resetContacts`/`seedContacts` создают данные у этого пользователя.

## Risks / Trade-offs

- [На сервере не добавили `OWNER_EMAIL` до выкатки] → Миграция падает до изменения базы, старый образ работает. В tasks строки `.env` — отдельный шаг владельца до merge.
- [Домен в Resend не подтверждён или ключ неверный] → Письма не уходят, войти нельзя, а данные уже с владельцем. Проверка: до merge владелец подтверждает домен в Resend; после выкатки — вход на проде своей почтой. Откат — только вместе с базой (см. Migration Plan).
- [Опечатка в `OWNER_EMAIL` на сервере] → Данные достаются почте, под которой никто не войдёт. Перед merge сверить строку; исправить можно разовым SQL-обновлением почты пользователя, без потери данных.
- [Better Auth изменит формат токена в `verifications`] → Отмена старых ссылок перестанет работать. Закрыто тестом на настоящей библиотеке; версия фиксируется в `pnpm-lock.yaml`.
- [Письмо держит транзакцию, пока идёт SMTP] → Блокировка по одной почте на секунду-две. При нескольких пользователях не заметно.
- [Предыдущий образ не работает с новой схемой] → Откат приложения без отката базы ломает прод. В README — откат только парой: restore бэкапа `deploy-*` перед выкаткой + прошлый образ.
- [Письма с нового домена попадают в спам] → Записи SPF/DKIM из Resend добавляет владелец; проверка — письмо на свою почту после выкатки.

## Migration Plan

До merge (делает владелец, агент говорит, что именно):

1. Аккаунт Resend, домен `mail.crm.chigabugadaga.ru`, записи DNS из Resend в reg.ru, домен подтверждён.
2. В `.env` на сервере: `OWNER_EMAIL`, `BETTER_AUTH_URL=https://app.chigabugadaga.ru`, `BETTER_AUTH_SECRET` (сгенерировать на сервере), `SMTP_URL` с ключом Resend.
3. Локально в `.env`: `OWNER_EMAIL`, `BETTER_AUTH_URL=http://localhost:3000`, `BETTER_AUTH_SECRET`, `SMTP_URL=smtp://127.0.0.1:1025`.
4. Миграция, меняющая данные, показана владельцу до merge (`CLAUDE.md`).

Выкатка — обычная: бэкап `deploy-*` → миграции → новый образ → smoke `/health`.

После выкатки: вход своей почтой на проде — видны все прежние контакты; число контактов, заметок и групп то же, что до выкатки (запрос в базу на сервере до и после).

Откат (запускает владелец, вручную): сначала `deploy.sh` с `previous-image`, затем `restore.sh` с бэкапом `deploy-*`, снятым этой выкаткой. Порядок такой, потому что `restore.sh` берёт текущий образ и применяет его миграции: с новым образом он заново применил бы миграцию входа. Между шагами приложение недолго не работает (старый образ не работает с новой схемой). По отдельности не откатывать: старый образ не работает с новой схемой, новый — со старой.
