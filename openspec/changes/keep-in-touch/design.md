# Design

## Context

Зачем это нужно — см. proposal.md, раздел Why; требования — `specs/keep-in-touch/spec.md`.

Что есть сейчас:

- Таблица `contacts` (имя, кто это, откуда знакомы, телефон, почта, `created_at`) и таблица `notes` (`contact_id`, `body`, `created_at`, `updated_at`). Индекс `notes (contact_id, created_at)` уже есть.
- Форма контакта одна на добавление и правку (`src/components/contact-form.tsx`). Поля описаны массивом `FIELDS`, проверка — схемой zod в `src/lib/contact-form.ts`, сохранение — `createContact`/`updateContact` в `src/app/actions.ts`.
- Главная (`src/app/page.tsx`) — серверная страница. Поиск и список стоят в одной границе `Suspense`: React показывает потоковые границы не чаще раза в 300 мс, поэтому отдельная граница появлялась бы с опозданием. Список строится на `LinkList`, чтобы не создавать сотни `<Link>`.
- Карточка (`src/app/contacts/[id]/page.tsx`) получает контакт и заметки (свежие первыми) через `getContactWithNotes`. Сведения о контакте выводит компонент `Detail`: пустое значение он показывает как «не указано».
- Даты в интерфейсе форматирует `formatDate` (`Intl`, ru-RU) в часовом поясе процесса Node. Явно часовой пояс нигде не задан, в контейнере на сервере это UTC.
- Тестового фреймворка в проекте нет; есть `typecheck`, `lint` и `tsx`.
- В тестовой базе 1000 контактов с заметками; генератор данных заполняет только пустую базу.

## Goals / Non-Goals

**Goals:**

- Одно место, где считается срок: и карточка, и блок на главной берут дату срока из одной функции, поэтому «связаться до …» в карточке и попадание в блок никогда не расходятся.
- Миграция только добавляет колонку. Предыдущий образ приложения работает с новой схемой, ручной откат образа не требует отката миграции.
- Главная не становится заметно медленнее при 1000 контактах.

**Non-Goals:**

- Менять генератор тестовых данных. Он заполняет только пустую базу, а локальная и серверная базы уже заполнены; для ручной проверки частоту задаём через форму или разовым SQL локально.
- Задавать часовой пояс приложения (см. Open Questions).
- Подключать тестовый фреймворк: это новая библиотека, её надо отдельно обсуждать. Расчёт сроков проверяем разовым скриптом через `tsx`, без коммита.

## Decisions

### 1. Частота хранится как enum в Postgres

Новая колонка `contacts.contact_frequency` типа `contact_frequency` (enum: `week`, `month`, `quarter`, `year`), `NULL` = «не задано». В Drizzle — `pgEnum`. Колонка без значения по умолчанию, поэтому все существующие контакты получают `NULL` и не попадают в блок.

- Почему не `text` с проверкой только в коде: база сама не даст записать мусор, а Drizzle выводит тип-объединение из enum, и TypeScript проверяет все места, где разбирается частота.
- Почему не число дней: «месяц» и «год» — календарные, а не фиксированное число дней (см. спеку, «Расчёт срока по календарю»).
- Цена: добавить новый вариант частоты потом — это миграция `ALTER TYPE … ADD VALUE`. Для четырёх стабильных вариантов это приемлемо.

### 2. Срок считается в TypeScript, а не в SQL

Чистые функции в новом файле `src/lib/keep-in-touch.ts`:

- список частот с подписями для формы, карточки и блока (`Раз в месяц` / `раз в месяц`);
- `dueDate(reference, frequency)` — календарная дата срока: берётся день точки отсчёта в местном времени, неделя = +7 дней, месяц/квартал/год = +1/3/12 месяцев с подрезкой до последнего дня месяца (31 января + месяц = 28 или 29 февраля);
- `isOverdue(due, today)` — сегодняшний день строго позже дня срока.

Почему не в SQL: даты в интерфейсе форматирует Node в своём часовом поясе, а у Postgres свой часовой пояс сессии. Если считать «какой сегодня день» в двух местах, карточка может показать «связаться до 12 октября», а блок уже считать контакт просроченным. Расчёт в одном месте, в том же поясе, что и `formatDate`, исключает такое расхождение. Объём маленький: даже если частота задана всем 1000 контактам, это 1000 строк и простая арифметика.

### 3. Выборка для блока — один запрос с группировкой

Новая функция в `src/lib/contacts.ts`: контакты с заданной частотой, `LEFT JOIN notes`, `max(notes.created_at)` как дата последней заметки, `GROUP BY contacts.id`. Использует существующий индекс `notes (contact_id, created_at)`. Дальше в TypeScript: точка отсчёта = последняя заметка или `contacts.created_at`, срок через `dueDate`, фильтр `isOverdue`, сортировка по сроку и при равенстве — по имени (`localeCompare` с локалью `ru`). Функция, как и остальные выборки, вызывает `connection()`, чтобы страница всегда читала свежие данные.

Отсчёт идёт только от `notes.created_at`, `updated_at` не участвует — так правка старой заметки не сбрасывает срок (спека, «Точка отсчёта срока»).

Альтернатива — хранить «дату последнего общения» в `contacts` и обновлять её при каждой новой заметке. Отказались: второй источник правды, который может разойтись с заметками; выигрыша в скорости на 1000 контактов нет.

### 4. Карточка считает срок из уже загруженных заметок

`getContactWithNotes` уже отдаёт заметки, свежие первыми, поэтому точка отсчёта — `notes[0]?.createdAt ?? contact.createdAt`. Отдельный запрос не нужен. Строка «Как часто общаться» — ещё один `Detail` в сетке сведений; если частоты нет, `Detail` сам покажет «не указано».

### 5. Поле в форме — нативный `<select>` в обёртке shadcn

Компонент `NativeSelect` из реестра shadcn (стиль `base-nova`) пишем в `src/components/ui/native-select.tsx` вручную по выводу `shadcn view native-select`: `shadcn add` перезаписывает наш `button.tsx`. Иконку-заглушку из реестра заменяем на `ChevronDownIcon` из lucide. Стили приводим к нашему `Input`: та же высота, скругление `rounded-field`, фон `bg-input`, отступы — только токены.

- Почему не выпадающий список shadcn `Select` на base-ui: нативный `<select>` работает без JavaScript, на телефоне открывает системный выбор, и его значение просто уходит в `FormData`, как у остальных полей формы.
- Почему не радиокнопки: пять вариантов в ряд не помещаются на телефоне, форма станет длиннее.

В форме: подпись «Как часто общаться — необязательно», варианты «Не задано» (пустое значение), «Раз в неделю», «Раз в месяц», «Раз в квартал», «Раз в год». Поле добавляется в `contactFields`, `emptyContactForm`, `contactFormFrom`; в схеме zod — enum или пустая строка, пустая строка превращается в `null`, как у других необязательных полей. `createContact`/`updateContact` и функции записи в базу менять не нужно: они уже передают весь разобранный объект.

### 6. Блок на главной — в той же границе `Suspense`

Серверный компонент блока ставится в `page.tsx` перед `ContactSearch`, внутри существующей границы `Suspense`, по той же причине, по которой там вместе стоят поиск и список. Когда просроченных нет, компонент ничего не выводит.

Кнопки «Показать всех» и «Свернуть» делает маленький клиентский компонент: сервер передаёт ему уже готовые строки (id, имя, подписи), он показывает первые 5, по «Показать всех» — все строки, по «Свернуть» — снова первые 5. После сворачивания компонент проверяет, где верх блока: если он выше экрана, прокручивает страницу к блоку (`scrollIntoView`), если блок виден — ничего не двигает. Так после сворачивания длинного списка я не оказываюсь посреди общего списка контактов. Состояние раскрытия в адрес не пишем: после перезагрузки блок снова свёрнут. Строки — через `LinkList` и обычные `<a>`, как в общем списке, оформление строк — как у общего списка.

### 7. После новой заметки обновлять и главную

`addNote` сейчас обновляет только карточку (`revalidatePath('/contacts/<id>')`). Добавляем `revalidatePath('/')`, чтобы после возврата на главную блок не показывал устаревшее состояние (спека, «Изменения видны сразу»). `createContact`, `updateContact` и `deleteContact` главную уже обновляют. `updateNote` не трогаем: правка заметки срок не меняет.

## Risks / Trade-offs

- [Часовой пояс сервера — UTC] → Граница дня на сервере проходит в 03:00 по Москве: заметка, написанная в 01:00 13 октября по Москве, считается написанной 12 октября. Это то же поведение, что уже есть у дат заметок в интерфейсе; расчёт сроков ему просто следует. Исправление — отдельной правкой, см. Open Questions.
- [Блок сдвигает поиск при загрузке] → Пока данные грузятся, заглушка показывает поиск и список без блока; когда блок появляется, поиск сдвигается вниз. Заглушку под блок не делаем: блока часто нет вовсе, и тогда сдвиг был бы обратным. Сдвиг один раз при загрузке, дальше блок стоит на месте.
- [Много просроченных] → В блоке видно первых 5, остальные спрятаны кнопкой; сервер всё равно отдаёт все строки. При 1000 контактах это несколько килобайт — приемлемо.
- [Добавить новый вариант частоты] → Нужна миграция enum. Приемлемо: варианты заданы в требованиях и меняются редко.

## Migration Plan

1. `pnpm db:generate` создаёт миграцию `drizzle/0002_*.sql`: `CREATE TYPE contact_frequency …` и `ALTER TABLE contacts ADD COLUMN contact_frequency contact_frequency`. Данные не меняются.
2. Локально: `pnpm db:migrate`, проверка руками.
3. Выкатка обычная: merge в main → образ → на сервере разовый контейнер применяет миграцию → стартует новый образ → smoke `/health`.
4. Откат — вручную, как в README: предыдущий образ не знает про новую колонку и просто её не читает, поэтому откатывать миграцию не нужно.

## Open Questions

- Часовой пояс приложения. Сейчас все даты (и заметок, и новые сроки) считаются по часовому поясу сервера — UTC. Если нужно по Москве, это отдельная небольшая правка (часовой пояс в образе или в форматировании дат), она затронет все даты в приложении. На требования и план этой фичи не влияет.
