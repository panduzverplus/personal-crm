# Личная CRM

Список людей, которых я знаю лично: кто это, откуда знакомы, телефон, почта и заметки о разговорах.
Идея и сценарии — в `specs/01-продуктовая-идея.md`.

## Что умеет

- Главная страница — список всех контактов по алфавиту и поиск по имени
  (регистр не важен, слова в любом порядке, «е» и «ё» не различаются)
- Под заголовком ряд кнопок: «Все» и по кнопке на каждую группу (в конце — ссылка «Настроить группы»).
  Выбрана одна группа — в списке только её контакты, над списком «В группе «Теннис»: 12 контактов».
  Группа выбирается и в блоке «Пора связаться» (в нём остаются только люди из группы), поиск работает внутри группы.
  Выбор хранится в адресе страницы, поэтому переживает обновление и открывается по той же ссылке в другом браузере.
  В строке списка мелким текстом видны группы контакта
- Если карточка открыта из списка с выбранной группой или поиском, ссылка вверху называется «Назад к списку» и ведёт к тому же
  списку: с той же группой и тем же запросом. Выбор сохраняется, пока вы работаете с контактом (заметки, «Изменить», «Отмена»,
  сохранение); после удаления контакта открывается тот же список с сообщением. После добавления нового контакта, как и раньше,
  открывается полный список. Если список не был сужен, ссылка остаётся «Все контакты»
- «Добавить контакт» — форма: имя (обязательно), кто это, откуда знакомы, телефон, почта
- Карточка контакта — все сведения и заметки; новая заметка добавляется сверху с датой и временем
  (кнопка «Добавить заметку» или Ctrl + Enter)
- Кнопка «Изменить» в карточке — поправить имя, «Кто это», «Откуда знакомы», телефон или почту;
  заметки при этом не меняются
- Кнопка «Удалить» в карточке — удалить контакт вместе с его заметками
  (после подтверждения; вернуть нельзя)
- Кнопка «Изменить» у заметки — поправить её текст прямо в карточке (сохранить — кнопкой или Ctrl + Enter,
  отменить — кнопкой или Esc); у изменённой заметки рядом с датой создания видно, когда её изменили
- Группы контакта — в форме (при добавлении и в «Изменить») поле «Группы» с галочкой на каждую группу: можно отметить
  несколько или ни одной. Под галочками поле «Новая группа» и кнопка «Создать» (или Enter): группа создаётся сразу,
  появляется отмеченной, а заполненные поля формы не теряются. Если закрыть форму кнопкой «Отмена», созданная группа остаётся.
  В карточке контакта есть строка «Группы» («Семья · Теннис», а если групп нет — «не указано»)
- Страница «Группы» (адрес `/groups`) — создать группу, переименовать («Изменить» в строке; «Сохранить», «Отмена» или Esc)
  и удалить («Удалить», после подтверждения). Названия не повторяются: «Теннис» и «теннис» — одно и то же, «е» и «ё» тоже;
  название обязательно, до 50 символов. При удалении группы контакты остаются, они только выходят из неё.
  Пять групп — «Семья», «Друзья», «Знакомые», «Теннис», «Аналитики» — есть только у владельца данных, которые были
  в базе до появления входа (их тоже можно менять и удалять); у новых пользователей групп нет
- Вход — по ссылке из письма, паролей нет. Без входа открываются только страница входа, страница «Ссылка устарела»
  и `/health`. Вводите почту на странице входа (регистр букв и пробелы по краям не важны) и нажимаете «Получить ссылку»:
  на неё приходит письмо «Вход в Личную CRM» с кнопкой «Войти». Ссылка работает один раз и 15 минут, новая ссылка
  отменяет старые, на одну почту — не больше 3 писем за 10 минут. Первый вход и есть регистрация: имя не спрашивается.
  Вход держится 30 дней с последнего захода на устройстве; устройств может быть несколько. В шапке — почта и «Выйти»
  (выход только на этом устройстве)
- Контакты, заметки и группы у каждого пользователя свои: чужое не видно в списке и поиске и не открывается по прямой
  ссылке («Контакт не найден»). У каждого свои группы, названия могут совпадать с чужими. Новый пользователь начинает
  с пустого списка и без групп
- Данные хранятся в базе PostgreSQL, поэтому в любом браузере видно одно и то же

## Что нужно установить

- Node.js 24
- pnpm
- Docker Desktop (в нём работают база данных и почтовая заглушка Mailpit)
- OpenSpec — для работы над требованиями фич: `npm install -g @fission-ai/openspec@latest`

## Настройки

Пароли и адрес базы лежат в файле `.env` (в git он не попадает). Образец — `.env.example`.
Приложение читает такие переменные:

| Переменная          | Что это                                                        |
| ------------------- | -------------------------------------------------------------- |
| `POSTGRES_USER`     | имя пользователя базы                                          |
| `POSTGRES_PASSWORD` | пароль базы                                                    |
| `POSTGRES_DB`       | название базы                                                  |
| `POSTGRES_PORT`     | порт, по умолчанию `5432`                                      |
| `DATABASE_URL`      | необязательно: полная строка подключения, заменяет всё, что выше |
| `BETTER_AUTH_SECRET` | секрет для входа: подписывает куки. Случайная строка, на компьютере — `openssl rand -base64 32` |
| `BETTER_AUTH_URL`   | адрес приложения: на компьютере `http://localhost:3000`, на сервере `https://app.chigabugadaga.ru` |
| `SMTP_URL`          | куда отправлять письма со ссылкой для входа: на компьютере `smtp://127.0.0.1:1025` (заглушка Mailpit), на сервере — SMTP Resend |
| `OWNER_EMAIL`       | почта владельца: ему достаются все контакты, которые были в базе до появления входа, и демо-данные. Нужна при `pnpm db:migrate` и `pnpm db:seed` |

## Первый запуск

Все команды выполняются в папке проекта.

```bash
pnpm install       # скачать библиотеки
pnpm db:up         # запустить базу данных и Mailpit в Docker
pnpm db:migrate    # создать таблицы (нужна OWNER_EMAIL в .env, см. ниже)
pnpm db:seed       # заполнить 1000 тестовыми контактами владельца (только если у него нет контактов)
pnpm build         # собрать приложение
pnpm start         # запустить
```

Откройте http://localhost:3000 — откроется страница входа.

### Как войти на компьютере

Письма на компьютере никуда не уходят: их принимает заглушка Mailpit, она запускается вместе с базой (`pnpm db:up`).

1. На странице входа введите любую почту (например, свою из `OWNER_EMAIL`, чтобы увидеть свои контакты) и нажмите «Получить ссылку»
2. Откройте http://localhost:8025 — это страница Mailpit со всеми «отправленными» письмами. Откройте письмо «Вход в Личную CRM»
3. Нажмите в письме «Войти» — вы внутри

Для настройки входа в `.env` нужны четыре строки (образец — `.env.example`):

```
OWNER_EMAIL=<ваша почта>
BETTER_AUTH_URL=http://localhost:3000
BETTER_AUTH_SECRET=<случайная строка: openssl rand -base64 32>
SMTP_URL=smtp://127.0.0.1:1025
```

`OWNER_EMAIL` — почта владельца: при `pnpm db:migrate` ему достаются все контакты, заметки и группы, которые уже были
в базе (пользователь с этой почтой создаётся сам, если его нет); ему же `pnpm db:seed` кладёт тестовые контакты.
Если в базе есть данные, а `OWNER_EMAIL` не задана, миграция остановится с ошибкой и ничего не изменит.

Чтобы остановить приложение — закройте окно, в котором оно запущено, или нажмите Ctrl + C.

## Тесты

```bash
pnpm db:up   # база должна работать
pnpm test
```

Тесты работают на настоящей базе, но не на вашей: перед запуском создаётся отдельная база
с именем рабочей и окончанием `_test` (например, `personal_crm_test`), в ней применяются все миграции.
Рабочие данные тесты не трогают. Если базы нет или она выключена, тесты не запустятся.

### E2e-тесты в браузере

Проходят сценарии так, как их проходит человек. Перед первым запуском один раз скачайте браузер:

```bash
pnpm exec playwright install chromium
```

Запуск:

```bash
pnpm db:up      # база и Mailpit должны работать
pnpm test:e2e
```

Команда сама создаёт отдельную базу с окончанием `_e2e_test`, собирает приложение и запускает его на порту 3100.
Запущенный `pnpm dev` ей не мешает, рабочие данные она не трогает. Тесты лежат в папке `e2e/`.

Входят тесты как человек: просят ссылку на странице входа, достают письмо из Mailpit и открывают ссылку
(`e2e/mailpit.ts`). Настоящих писем не уходит. Сроки (15 минут, 10 минут, 30 дней) тесты не ждут, а сдвигают в базе.

## Как устроено

- `src/app` — страницы: список (`page.tsx`), новый контакт (`contacts/new`), карточка (`contacts/[id]`),
  изменение контакта (`contacts/[id]/edit`), группы (`groups`) и серверные действия (`actions.ts`)
- `src/components` — части интерфейса
- Оформление — в одном стиле с лендингом: цвета, шрифты, размеры текста и скругления заданы в `src/app/globals.css`,
  шрифты подключены в `src/app/layout.tsx`
- `src/lib/contacts.ts` и `src/lib/groups.ts` — запросы к базе; браузер к базе не обращается, всё идёт через сервер.
  Каждая функция первым параметром получает id пользователя и сама отбирает только его данные; id берётся из сессии
  (`requireUser()`), а не из браузера
- Вход (Better Auth, плагин magic link):
  - `src/lib/auth.ts` — настройки входа, сроки, лимит писем на почту и отмена старых ссылок (`sendMagicLink`);
    обработчик — `src/app/api/auth/[...all]/route.ts`
  - `src/lib/session.ts` — `requireUser()`: первая строка каждой страницы с данными и каждого серверного действия
  - `src/proxy.ts` — гость без куки уходит на страницу входа; куку входа обновляет при каждом заходе
    (это удобство, а не защита: защита — `requireUser()`)
  - `src/lib/mail.ts` и `src/lib/login-email.ts` — письмо и его отправка (Nodemailer; куда слать — решает `SMTP_URL`);
    там же проверка почты
  - `src/app/login` и `src/app/login/expired` — страницы «Вход» и «Ссылка устарела»
- `src/db` — схема таблиц (`auth-schema.ts` — таблицы входа), подключение, применение миграций (`migrate.ts`),
  генератор тестовых данных
- `src/app/health/route.ts` — адрес `/health`: отвечает 200, если приложение работает и достаёт до базы
- `drizzle/` — миграции базы
- `src/test` — подготовка тестов: создание тестовой базы, очистка таблиц, заглушки для `server-only` и `connection()`;
  сами тесты лежат рядом с кодом, в файлах `*.test.ts`
- `e2e/` — e2e-тесты Playwright, настройки — в `playwright.config.ts`
- `openspec/` — требования фич (OpenSpec, тексты на русском): действующие — в `specs/`, новые и в работе — в `changes/`,
  настройки — в `config.yaml`. Команды для Claude Code — `/opsx:propose`, `/opsx:apply`, `/opsx:archive` и другие в `.claude/commands/opsx/`
- `Dockerfile` — образ приложения; его собирает GitHub Actions
- `.github/workflows/deploy-staging.yml` (merge в main → тест-стенд), `.github/workflows/deploy-prod.yml` (прод, по кнопке)
  и `deploy/` — скрипты выкатки, бэкапа и восстановления
- `deploy/server/` — подготовка сервера: скрипт, настройки nginx и Docker, страница-заглушка

## Выкатка

Merge в `main` выкатывает только на тест-стенд. На прод версия едет только кнопкой — её нажимаете вы.

### Как выкатить на прод

1. Влейте PR в `main` и дождитесь зелёного запуска **Deploy staging** (вкладка Actions): образ собран и выкачен на стенд.
   Проверьте стенд руками: https://test-app.chigabugadaga.ru (пароль на сайт — у вас)
2. Actions → **Deploy prod** → Run workflow → оставьте поле `sha` пустым и галочку `rollback` не ставьте → Run workflow.
   То же из терминала: `gh workflow run "Deploy prod"`
3. Дождитесь зелёной галочки (обычно 2–3 минуты, смотреть — `gh run watch`). В итогах запуска (Summary внизу страницы
   запуска) написано, какой SHA выкатился. Проверьте https://app.chigabugadaga.ru

Что выкатится:

- поле `sha` пустое — версия последней зелёной выкатки на тест-стенд, то есть то, что вы только что проверили
- `sha` вручную (запасной путь: например, выкатить не последнюю версию) — только если по нему был зелёный запуск
  **Deploy staging**. Иначе запуск сразу падает с понятной ошибкой, прод не трогается:
  `gh workflow run "Deploy prod" -f sha=<SHA коммита>`

На сервере при выкатке прода (`deploy.sh prod`):

1. Следит, чтобы стоял ежедневный бэкап (см. «Бэкапы и восстановление»)
2. Снимает бэкап базы скриптом `backup.sh`. Если бэкап не получился — выкатка останавливается, работает старая версия
3. Применяет миграции разовым контейнером из нового образа.
   Если миграции упали — новый образ не запускается, продолжает работать старый
4. Запускает новый образ и проверяет, что https://app.chigabugadaga.ru/health отвечает 200
5. Чистит старые образы (см. ниже)

Красный запуск — выкатка упала. Сама она ничего не откатывает: смотрите ошибку в запуске и решайте, откатывать ли.
Два запуска **Deploy prod** одновременно не идут: второй ждёт первый (очередь в GitHub Actions и замок на сервере).

### Как откатить прод

Actions → **Deploy prod** → Run workflow → поставьте галочку `rollback` (поле `sha` в этом случае не смотрится) → Run workflow.
То же из терминала: `gh workflow run "Deploy prod" -f rollback=true`

Прод вернётся на версию, которая стояла до текущей: её помнит сервер (`previous-image`), образ лежит на сервере, тест-стенд
не проверяется. Перед откатом снимается бэкап базы. В итогах запуска написано, на какой SHA откатились.
Миграции откат не отменяет: база остаётся той, какой её сделала новая версия. Если нужно вернуть и данные —
см. «Восстановление базы из бэкапа». После отката «предыдущей» становится версия, с которой откатились: повторный откат
вернёт её обратно.

Запасной путь, если GitHub недоступен (то же самое с сервера):

```bash
ssh crm 'bash ~/personal-crm/deploy.sh prod "$(cat ~/personal-crm/previous-image)"'
```

### Чистка старых образов

Запускается после удачной выкатки прода вперёд (после отката — только чистка на сервере):

- на сервере удаляются образы старше 2 недель, кроме двух последних версий прода и текущей версии стенда:
  откат на прошлую версию прода работает всегда
- в GHCR остаются 10 последних сборок и только что выкаченная; остальные версии пакета удаляются
  (отдельная задача `cleanup-ghcr` в запуске **Deploy prod**; если она красная, прод при этом выкачен нормально)

### Команды и файлы на сервере

| Что сделать                                  | Команда                                                                                        |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| посмотреть, какой образ сейчас на сервере    | `ssh crm 'cat ~/personal-crm/current-image'` (прод), `staging-current-image` (стенд)           |
| посмотреть логи приложения                   | `ssh crm 'docker logs --tail 100 prod-crm-app-1'` (прод), `staging-crm-app-1` (стенд); историю — см. «Логи» ниже |
| заполнить пустую базу 1000 тестовыми контактами | `ssh crm 'cd ~/personal-crm && APP_IMAGE=$(cat current-image) docker compose -p prod run --rm crm-seed'` |
| посмотреть бэкапы базы                       | `ssh crm 'ls -lh ~/personal-crm/backups'`                                                      |
| снять бэкап базы вручную                     | `ssh crm 'bash ~/personal-crm/backup.sh'`                                                 |

На сервере всё лежит в `~/personal-crm/`: копия папки `deploy/` из репозитория (`compose.yaml`, `deploy.sh`,
`restore.sh`, `lib.sh` и другое), а ещё файлы, которых в git нет: `current-image`, `previous-image`,
`staging-current-image`, папка `backups/`, замки `deploy-*.lock`, журнал ежедневного бэкапа `backup-cron.log` и файлы настроек: `.env` прода и `.env.staging` стенда
(права 600, создаются вручную, в git не попадают). `.env` прода:

```
POSTGRES_USER=crm
POSTGRES_PASSWORD=<случайный пароль>
POSTGRES_DB=crm
OWNER_EMAIL=<почта владельца>
BETTER_AUTH_URL=https://app.chigabugadaga.ru
BETTER_AUTH_SECRET=<случайная строка: openssl rand -base64 32>
SMTP_URL=smtps://resend:<API-ключ Resend>@smtp.resend.com:465
```

Эти четыре строки нужны до выкатки входа. Без `OWNER_EMAIL` миграция остановится с ошибкой, и новая версия не запустится
(работает прежняя). Письма на сервере уходят через Resend с адреса `noreply@mail.crm.chigabugadaga.ru`: домен
`mail.crm.chigabugadaga.ru` должен быть подтверждён в Resend (записи DNS в reg.ru).

База PostgreSQL работает на сервере в Docker, её данные хранятся в томе `prod_crm-db-data`.

Для выкатки в GitHub заведены секрет `DEPLOY_SSH_KEY` (приватный ключ деплоя) и переменные
`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS`.

## Логи

Логи всех контейнеров (приложение и база, прод и стенд) идут в журнал сервера (journald). Они не удаляются вместе
с контейнером, поэтому переживают выкатку и откат. Размер журнала ограничивает сама система: старые строки удаляются,
диск не забивается. Метка строк в журнале — имя контейнера: `prod-crm-app-1`, `prod-crm-db-1`,
`staging-crm-app-1`, `staging-crm-db-1`.

```bash
ssh crm 'docker logs --tail 100 prod-crm-app-1'                     # что сейчас: последние 100 строк работающего контейнера
ssh crm 'journalctl -t prod-crm-app-1 -n 200 --no-pager'            # история, в том числе уже заменённых контейнеров
ssh crm 'journalctl -t prod-crm-app-1 --since "1 hour ago" --no-pager'   # за последний час
ssh crm 'journalctl -t staging-crm-app-1 -n 200 --no-pager'         # стенд; для базы — prod-crm-db-1
```

`journalctl` работает, если пользователь `crmapp` в группе `systemd-journal`
(один раз: `ssh -t crm "sudo usermod -aG systemd-journal crmapp"`).

## Бэкапы и восстановление

### Бэкапы

Бэкап снимает скрипт `backup.sh`. Бэкапы лежат на сервере в `~/personal-crm/backups/`
(папка и файлы доступны только пользователю `crmapp`).

Имя файла — вид бэкапа, время снятия (UTC) и версия приложения, которая работала в этот момент (короткий SHA коммита):

```
deploy-20261110-142530-e395423.dump
вид    дата     время  версия
```

| Вид              | Когда снимается                                              | Сколько хранится                 |
| ---------------- | ------------------------------------------------------------ | -------------------------------- |
| `daily-`         | каждые сутки в 03:00 по Москве (в имени время UTC, то есть `-0000`); версия — та, что работает сейчас | 7 последних, старые удаляются сразу после нового бэкапа |
| `deploy-`        | каждая выкатка и откат прода, первым шагом — до миграций; версия — та, что стояла **до** выкатки | 7 последних, старые удаляются сразу после нового бэкапа |
| `manual-`        | вручную, командой ниже                                       | не удаляются, чистите сами       |
| `before-restore-` | восстановление, перед удалением базы                        | не удаляются, чистите сами       |

На самой первой выкатке версии ещё нет — в имени будет `none`.

#### Ежедневный бэкап

Запускает cron пользователя `crmapp`: строка в его crontab (`CRON_TZ=Europe/Moscow`, `0 3 * * *`) вызывает
`daily-backup.sh`. Если в этот момент идёт выкатка прода, бэкап ждёт её конца. Строку ставит сама выкатка прода
(`install-backup-cron.sh`, повторный запуск ничего не дублирует), отдельно настраивать ничего не нужно.
Нужен только установленный на сервере `cron` (на Ubuntu он есть; нет — выкатка скажет: `sudo apt install cron`).

Проверить, что бэкап настроен и работает:

```bash
ssh crm 'crontab -l'                              # строка с daily-backup.sh и CRON_TZ=Europe/Moscow
ssh crm 'ls -lh ~/personal-crm/backups | grep daily'   # файлы daily-…-0000-….dump, по одному в сутки
ssh crm 'tail -20 ~/personal-crm/backup-cron.log'      # журнал запусков, ошибки тоже здесь
ssh crm 'bash ~/personal-crm/daily-backup.sh'          # снять такой бэкап прямо сейчас
```

Снять бэкап вручную (например, перед тем как что-то делать с базой руками):

```bash
ssh crm 'bash ~/personal-crm/backup.sh'
```

Скрипт напишет, куда сохранил файл, например `.../backups/manual-20261110-150000-e395423.dump`.

Посмотреть список, скачать бэкап к себе на компьютер и удалить ненужный:

```bash
ssh crm 'ls -lh ~/personal-crm/backups'
scp crm:personal-crm/backups/deploy-20261110-142530-e395423.dump .
ssh crm 'rm ~/personal-crm/backups/manual-20261110-150000-e395423.dump'
```

Бэкапы хранятся только на этом сервере: если сервер пропадёт, пропадут и они. Важный бэкап лучше скачать к себе.

### Восстановление базы из бэкапа

Запускаете только вы, вручную. Скрипт заменяет всю базу прода содержимым файла бэкапа:

```bash
ssh -t crm 'bash ~/personal-crm/restore.sh ~/personal-crm/backups/deploy-20261110-142530-e395423.dump'
```

(`-t` нужен, чтобы ответить на вопрос скрипта.)

Что делает скрипт:

1. Проверяет, что файл — настоящий бэкап базы
2. Показывает, какой файл загрузит, какую базу заменит и какая версия приложения останется,
   и ждёт, пока вы введёте `yes`. Любой другой ответ — выход, ничего не меняется
3. Снимает копию текущей базы: `backups/before-restore-<дата>-<версия>.dump`.
   Такие копии сами не удаляются (см. таблицу выше)
4. Останавливает приложение
5. Удаляет базу, создаёт пустую и загружает в неё бэкап
6. Применяет миграции текущей версии (бэкап снят до миграций выкатки, поэтому схема в нём может быть старее)
7. Поднимает приложение той же версии и проверяет, что https://app.chigabugadaga.ru/health отвечает 200

Версию приложения скрипт не меняет. Если какой-то шаг упал — скрипт останавливается, сам ничего не откатывает
(приложение может остаться остановленным) и пишет, где лежит копия базы из шага 3. Её можно восстановить тем же скриптом.

Если нужно откатить и версию, и данные (например, миграция испортила данные):
сначала откатите образ (кнопка `rollback` в **Deploy prod**, см. «Как откатить прод»), потом запустите восстановление с бэкапом,
в имени которого стоит эта предыдущая версия.

#### Откат выкатки входа — только парой

Выкатка входа меняет схему базы: у контактов и групп появляется владелец, появляются таблицы входа. Прежний образ
с такой схемой не работает, а новый образ не работает со старой. Поэтому откатывать только вместе:

1. Верните прежний образ: **Deploy prod** с галочкой `rollback` (или запасной командой по ssh из «Как откатить прод»)
2. Восстановите базу из бэкапа `deploy-…`, снятого перед выкаткой входа (в имени — SHA прежней версии),
   командой `restore.sh` из раздела выше

Порядок важен: `restore.sh` берёт тот образ, который сейчас стоит, и применяет его миграции. Если восстановить базу,
пока стоит новый образ, он снова применит миграцию входа, и ничего не откатится. Между шагами 1 и 2 приложение
недолго не работает: прежний образ не работает с новой схемой. По отдельности не откатывайте.

## Сервер

Сервер `153.76.175.154`, вход — `ssh crm` (пользователь `crmapp`; вход под root и по паролю закрыт).
Команды с `sudo` спрашивают пароль crmapp.

- `chigabugadaga.ru` — лендинг (пока заглушка), `app.chigabugadaga.ru` — приложение, `test-app.chigabugadaga.ru` — тест-стенд (под паролем)
- Один сертификат Let's Encrypt на лендинг и приложение, отдельный — на стенд; оба продлеваются сами (таймер `certbot.timer`);
  http перенаправляется на https
- Docker открывает порты контейнеров только на `127.0.0.1`: наружу всё идёт через nginx.
  Логи контейнеров идут в журнал сервера (см. «Логи» ниже); лимит Docker «3 файла по 10 МБ» остаётся только запасным
  для контейнеров, у которых драйвер логов не задан
- Docker сам не обновляется: обновлять вручную через `sudo apt upgrade`
- Пользователь `crmapp` в группе `docker`, чтобы выкатка работала без sudo

Подготовка сервера с нуля (повторный запуск ничего не ломает):

```bash
scp -r deploy/server crm:server-setup
ssh -t crm "sudo bash ~/server-setup/setup-server.sh <почта для Let's Encrypt>"
```

Журнал последнего запуска — `/var/log/server-setup.log` на сервере.
