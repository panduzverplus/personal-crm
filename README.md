# Личная CRM

Список людей, которых я знаю лично: кто это, откуда знакомы, телефон, почта и заметки о разговорах.
Идея и сценарии — в `specs/01-продуктовая-идея.md`.

## Что умеет

- Главная страница — список всех контактов по алфавиту и поиск по имени
  (регистр не важен, слова в любом порядке, «е» и «ё» не различаются)
- Под заголовком ряд кнопок: «Все» и по кнопке на каждую группу (в конце — ссылка «Настроить группы»).
  Выбрана одна группа — в списке только её контакты, над списком «В группе «Теннис»: 12 контактов».
  Группа выбирается и в блоке «Пора связаться» (в нём остаются только люди из группы), поиск работает внутри группы.
  Выбор хранится в адресе страницы, поэтому переживает обновление и открывается по той же ссылке в другом браузере.
  В строке списка мелким текстом видны группы контакта
- Если карточка открыта из списка с выбранной группой или поиском, ссылка вверху называется «Назад к списку» и ведёт к тому же
  списку: с той же группой и тем же запросом. Выбор сохраняется, пока вы работаете с контактом (заметки, «Изменить», «Отмена»,
  сохранение); после удаления контакта открывается тот же список с сообщением. После добавления нового контакта, как и раньше,
  открывается полный список. Если список не был сужен, ссылка остаётся «Все контакты»
- «Добавить контакт» — форма: имя (обязательно), кто это, откуда знакомы, телефон, почта
- Карточка контакта — все сведения и заметки; новая заметка добавляется сверху с датой и временем
  (кнопка «Добавить заметку» или Ctrl + Enter)
- Кнопка «Изменить» в карточке — поправить имя, «Кто это», «Откуда знакомы», телефон или почту;
  заметки при этом не меняются
- Кнопка «Удалить» в карточке — удалить контакт вместе с его заметками
  (после подтверждения; вернуть нельзя)
- Кнопка «Изменить» у заметки — поправить её текст прямо в карточке (сохранить — кнопкой или Ctrl + Enter,
  отменить — кнопкой или Esc); у изменённой заметки рядом с датой создания видно, когда её изменили
- Группы контакта — в форме (при добавлении и в «Изменить») поле «Группы» с галочкой на каждую группу: можно отметить
  несколько или ни одной. Под галочками поле «Новая группа» и кнопка «Создать» (или Enter): группа создаётся сразу,
  появляется отмеченной, а заполненные поля формы не теряются. Если закрыть форму кнопкой «Отмена», созданная группа остаётся.
  В карточке контакта есть строка «Группы» («Семья · Теннис», а если групп нет — «не указано»)
- Страница «Группы» (адрес `/groups`) — создать группу, переименовать («Изменить» в строке; «Сохранить», «Отмена» или Esc)
  и удалить («Удалить», после подтверждения). Названия не повторяются: «Теннис» и «теннис» — одно и то же, «е» и «ё» тоже;
  название обязательно, до 50 символов. При удалении группы контакты остаются, они только выходят из неё.
  Сразу после выкатки есть пять групп: «Семья», «Друзья», «Знакомые», «Теннис», «Аналитики» — их тоже можно менять и удалять
- Данные хранятся в базе PostgreSQL, поэтому в любом браузере видно одно и то же

## Что нужно установить

- Node.js 24
- pnpm
- Docker Desktop (в нём работает база данных)
- OpenSpec — для работы над требованиями фич: `npm install -g @fission-ai/openspec@latest`

## Настройки

Пароли и адрес базы лежат в файле `.env` (в git он не попадает). Образец — `.env.example`.
Приложение читает такие переменные:

| Переменная          | Что это                                                        |
| ------------------- | -------------------------------------------------------------- |
| `POSTGRES_USER`     | имя пользователя базы                                          |
| `POSTGRES_PASSWORD` | пароль базы                                                    |
| `POSTGRES_DB`       | название базы                                                  |
| `POSTGRES_PORT`     | порт, по умолчанию `5432`                                      |
| `DATABASE_URL`      | необязательно: полная строка подключения, заменяет всё, что выше |

## Первый запуск

Все команды выполняются в папке проекта.

```bash
pnpm install       # скачать библиотеки
pnpm db:up         # запустить базу данных в Docker
pnpm db:migrate    # создать таблицы
pnpm db:seed       # заполнить 1000 тестовыми контактами (только если база пустая)
pnpm build         # собрать приложение
pnpm start         # запустить
```

Откройте http://localhost:3000.

Чтобы остановить приложение — закройте окно, в котором оно запущено, или нажмите Ctrl + C.

## Следующие запуски

```bash
pnpm db:up
pnpm start
```

Если код менялся — перед `pnpm start` выполните `pnpm build`.

## Тесты

```bash
pnpm db:up   # база должна работать
pnpm test
```

Тесты работают на настоящей базе, но не на вашей: перед запуском создаётся отдельная база
с именем рабочей и окончанием `_test` (например, `personal_crm_test`), в ней применяются все миграции.
Рабочие данные тесты не трогают. Если базы нет или она выключена, тесты не запустятся.

### E2e-тесты в браузере

Проходят сценарии так, как их проходит человек. Перед первым запуском один раз скачайте браузер:

```bash
pnpm exec playwright install chromium
```

Запуск:

```bash
pnpm db:up      # база должна работать
pnpm test:e2e
```

Команда сама создаёт отдельную базу с окончанием `_e2e_test`, собирает приложение и запускает его на порту 3100.
Запущенный `pnpm dev` ей не мешает, рабочие данные она не трогает. Тесты лежат в папке `e2e/`.

## Как устроено

- `src/app` — страницы: список (`page.tsx`), новый контакт (`contacts/new`), карточка (`contacts/[id]`),
  изменение контакта (`contacts/[id]/edit`), группы (`groups`) и серверные действия (`actions.ts`)
- `src/components` — части интерфейса
- Оформление — в одном стиле с лендингом: цвета, шрифты, размеры текста и скругления заданы в `src/app/globals.css`,
  шрифты подключены в `src/app/layout.tsx`
- `src/lib/contacts.ts` и `src/lib/groups.ts` — запросы к базе; браузер к базе не обращается, всё идёт через сервер
- `src/db` — схема таблиц, подключение, применение миграций на сервере (`migrate.ts`), генератор тестовых данных
- `src/app/health/route.ts` — адрес `/health`: отвечает 200, если приложение работает и достаёт до базы
- `drizzle/` — миграции базы
- `src/test` — подготовка тестов: создание тестовой базы, очистка таблиц, заглушки для `server-only` и `connection()`;
  сами тесты лежат рядом с кодом, в файлах `*.test.ts`
- `e2e/` — e2e-тесты Playwright, настройки — в `playwright.config.ts`
- `openspec/` — требования фич (OpenSpec, тексты на русском): действующие — в `specs/`, новые и в работе — в `changes/`,
  настройки — в `config.yaml`. Команды для Claude Code — `/opsx:propose`, `/opsx:apply`, `/opsx:archive` и другие в `.claude/commands/opsx/`
- `Dockerfile` — образ приложения; его собирает GitHub Actions
- `.github/workflows/deploy.yml` и `deploy/` — автовыкатка на сервер
- `deploy/server/` — подготовка сервера: скрипт, настройки nginx и Docker, страница-заглушка

## Выкатка

Чтобы выкатить новую версию, отправьте коммит в ветку `main`:

```bash
git push
```

Дальше всё идёт само, обычно 3–5 минут:

1. GitHub Actions собирает образ приложения с тегом — SHA коммита — и кладёт его в GHCR
   (`ghcr.io/panduzverplus/personal-crm`)
2. Заходит на сервер по ключу деплоя, копирует туда всю папку `deploy/` и запускает `deploy.sh`
3. `deploy.sh` снимает бэкап базы скриптом `backup.sh` (подробнее — в разделе «Бэкапы и восстановление»).
   Если бэкап не получился — выкатка останавливается, продолжает работать старая версия
4. Применяет миграции разовым контейнером из нового образа.
   Если миграции упали — новый образ не запускается, продолжает работать старый
5. Запускает новый образ и проверяет, что https://app.chigabugadaga.ru/health отвечает 200
6. Оставляет на сервере только текущий и предыдущий образы и 10 последних бэкапов выкатки

Ход выкатки — на вкладке Actions репозитория или командой `gh run watch`.
Зелёная галочка — новая версия на сервере. Красный крестик — выкатка упала; сама она ничего не откатывает.

Ручной откат на предыдущий образ (миграции он не отменяет; перед откатом тоже снимается бэкап):

```bash
ssh crm 'bash ~/personal-crm/deploy.sh $(cat ~/personal-crm/previous-image)'
```

Другие команды:

| Что сделать                                  | Команда                                                                                        |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| посмотреть, какой образ сейчас на сервере    | `ssh crm 'cat ~/personal-crm/current-image'`                                                   |
| посмотреть логи приложения                   | `ssh crm 'docker logs --tail 100 prod-crm-app-1'`                                              |
| заполнить пустую базу 1000 тестовыми контактами | `ssh crm 'cd ~/personal-crm && APP_IMAGE=$(cat current-image) docker compose -p prod run --rm crm-seed'` |
| посмотреть бэкапы базы                       | `ssh crm 'ls -lh ~/personal-crm/backups'`                                                      |
| снять бэкап базы вручную                     | `ssh crm 'bash ~/personal-crm/backup.sh'`                                                 |

На сервере всё лежит в `~/personal-crm/`: копия папки `deploy/` из репозитория (`compose.yaml`, `deploy.sh`,
`restore.sh`, `lib.sh` и другое), а ещё файлы, которых в git нет: `current-image`, `previous-image`, папка `backups/`
и `.env` с паролем базы (права 600, создаётся вручную, в git не попадает):

```
POSTGRES_USER=crm
POSTGRES_PASSWORD=<случайный пароль>
POSTGRES_DB=crm
```

База PostgreSQL работает на сервере в Docker, её данные хранятся в томе `prod_crm-db-data`.

Для выкатки в GitHub заведены секрет `DEPLOY_SSH_KEY` (приватный ключ деплоя) и переменные
`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS`.

## Бэкапы и восстановление

### Бэкапы

Бэкап снимает скрипт `backup.sh`. Бэкапы лежат на сервере в `~/personal-crm/backups/`
(папка и файлы доступны только пользователю `crmapp`).

Имя файла — вид бэкапа, время снятия (UTC) и версия приложения, которая работала в этот момент (короткий SHA коммита):

```
deploy-20261110-142530-e395423.dump
вид    дата     время  версия
```

| Вид              | Когда снимается                                              | Сколько хранится                 |
| ---------------- | ------------------------------------------------------------ | -------------------------------- |
| `deploy-`        | каждая выкатка, первым шагом — до миграций; версия — та, что стояла **до** выкатки | 10 последних, старые удаляются после удачной выкатки |
| `manual-`        | вручную, командой ниже                                       | не удаляются, чистите сами       |
| `before-restore-` | восстановление, перед удалением базы                        | не удаляются, чистите сами       |

На самой первой выкатке версии ещё нет — в имени будет `none`.

Снять бэкап вручную (например, перед тем как что-то делать с базой руками):

```bash
ssh crm 'bash ~/personal-crm/backup.sh'
```

Скрипт напишет, куда сохранил файл, например `.../backups/manual-20261110-150000-e395423.dump`.

Посмотреть список, скачать бэкап к себе на компьютер и удалить ненужный:

```bash
ssh crm 'ls -lh ~/personal-crm/backups'
scp crm:personal-crm/backups/deploy-20261110-142530-e395423.dump .
ssh crm 'rm ~/personal-crm/backups/manual-20261110-150000-e395423.dump'
```

Бэкапы хранятся только на этом сервере: если сервер пропадёт, пропадут и они. Важный бэкап лучше скачать к себе.

### Восстановление базы из бэкапа

Запускаете только вы, вручную. Скрипт заменяет всю базу прода содержимым файла бэкапа:

```bash
ssh -t crm 'bash ~/personal-crm/restore.sh ~/personal-crm/backups/deploy-20261110-142530-e395423.dump'
```

(`-t` нужен, чтобы ответить на вопрос скрипта.)

Что делает скрипт:

1. Проверяет, что файл — настоящий бэкап базы
2. Показывает, какой файл загрузит, какую базу заменит и какая версия приложения останется,
   и ждёт, пока вы введёте `yes`. Любой другой ответ — выход, ничего не меняется
3. Снимает копию текущей базы: `backups/before-restore-<дата>-<версия>.dump`.
   Такие копии сами не удаляются (см. таблицу выше)
4. Останавливает приложение
5. Удаляет базу, создаёт пустую и загружает в неё бэкап
6. Применяет миграции текущей версии (бэкап снят до миграций выкатки, поэтому схема в нём может быть старее)
7. Поднимает приложение той же версии и проверяет, что https://app.chigabugadaga.ru/health отвечает 200

Версию приложения скрипт не меняет. Если какой-то шаг упал — скрипт останавливается, сам ничего не откатывает
(приложение может остаться остановленным) и пишет, где лежит копия базы из шага 3. Её можно восстановить тем же скриптом.

Если нужно откатить и версию, и данные (например, миграция испортила данные):
сначала откатите образ (команда «Ручной откат» выше), потом запустите восстановление с бэкапом,
в имени которого стоит эта предыдущая версия.

## Сервер

Сервер `153.76.175.154`, вход — `ssh crm` (пользователь `crmapp`; вход под root и по паролю закрыт).
Команды с `sudo` спрашивают пароль crmapp.

- `chigabugadaga.ru` — лендинг (пока заглушка), `app.chigabugadaga.ru` — приложение
- Один сертификат Let's Encrypt на оба домена, продлевается сам (таймер `certbot.timer`);
  http перенаправляется на https
- Docker открывает порты контейнеров только на `127.0.0.1`: наружу всё идёт через nginx.
  Логи контейнеров ограничены: до 3 файлов по 10 МБ
- Docker сам не обновляется: обновлять вручную через `sudo apt upgrade`
- Пользователь `crmapp` в группе `docker`, чтобы выкатка работала без sudo

Подготовка сервера с нуля (повторный запуск ничего не ломает):

```bash
scp -r deploy/server crm:server-setup
ssh -t crm "sudo bash ~/server-setup/setup-server.sh <почта для Let's Encrypt>"
```

Журнал последнего запуска — `/var/log/server-setup.log` на сервере.
